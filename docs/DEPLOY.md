# Публикация на GitHub Pages

## Конфигурация

- Репозиторий: `MrDary-art/slang-os`.
- Ветка публикации: `main`.
- Базовый путь Vite: `/slang-os/`.
- Результат сборки: `dist/`.
- Целевой URL: `https://mrdary-art.github.io/slang-os/`.

Целевой URL — ожидаемое расположение проекта. Он не означает, что текущая версия уже опубликована.

## Один раз в настройках репозитория

Откройте **Settings → Pages → Build and deployment** и выберите **Source: GitHub Actions**. При наличии правил environment `github-pages` проверьте, что они допускают deployment из `main`.

Порядок соответствует [официальной документации GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

## Автоматическая публикация

После push в `main` workflow `.github/workflows/deploy.yml`:

1. Получает исходники и настраивает Node.js 22 с кешем npm.
2. Выполняет `npm ci` по `package-lock.json`.
3. Выполняет `npm test`.
4. Выполняет `npm run build`: TypeScript должен проверяться перед production-сборкой.
5. Настраивает Pages и загружает `dist/` через официальный `upload-pages-artifact`.
6. Публикует артефакт отдельной задачей `deploy-pages`.

Workflow можно запустить вручную в **Actions → Verify and deploy GitHub Pages → Run workflow**. Секреты вручную добавлять не требуется: используются временный `GITHUB_TOKEN` и OIDC. Право чтения исходников — `contents: read`; задача публикации получает `pages: write` и `id-token: write`.

## Локальная проверка production

```bash
npm ci
npm test
npm run build
npm run preview
```

Откройте напечатанный адрес с путём `/slang-os/`. Проверьте главную, старт игры, архив, исследование и обновление страницы внутри маршрута. Статические ресурсы должны загружаться из базового пути; корневые ссылки вида `/assets/...` для этого проекта не подходят.

## Как подтвердить deployment

1. Вкладка **Actions**: задачи `build` и `deploy` завершены успешно.
2. В environment **github-pages** откройте URL из результата задачи.
3. В новом окне браузера проверьте старт расследования, поиск слов и переход в исследование.
4. Обновите страницу внутри раздела. Убедитесь, что GitHub не возвращает 404.
5. Проверьте мобильную ширину и печать исследования.

Не сообщайте жюри о публикации до этих проверок. Если доступ к GitHub у исполнителя отсутствует, достаточно подготовить изменения локально; пользователь с доступом должен отправить их в `main` и включить Pages.

## Если что-то не работает

| Симптом | Что проверить |
| --- | --- |
| `npm ci` сообщает несовпадение lockfile | Согласовать `package.json` и `package-lock.json` через `npm install`, затем сохранить оба файла |
| TypeScript или тесты не прошли | Исправить ошибку в build job; непроверенную сборку не публиковать |
| Pages возвращает 404 | Включён ли источник GitHub Actions, успешен ли deploy, совпадают ли имя репозитория и Vite base |
| Не загружаются JS/CSS | Правилен ли `/slang-os/`, нет ли путей от корня домена |
| Главная работает, внутренний адрес нет | Используется ли маршрутизация, пригодная для статического хостинга; проверьте hash-переходы |
| Публикация ожидает approval | Проверить реальные правила environment `github-pages` в GitHub |
| Локально виден старый прогресс | Это сохранение браузера; сбросить его через настройки игры с подтверждением |

Публичный хостинг не синхронизирует `localStorage` между устройствами. Загрузка новой версии не должна намеренно очищать совместимое сохранение.
